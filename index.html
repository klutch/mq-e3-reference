A · Sources & Method
Read this first. Two commands do the same job in E3: /bark repeats your text 5× on EMU servers, while /e3bark says it exactly once. Same pattern shows up elsewhere — where an /e3-prefixed twin exists it is usually the newer, saner one. 1.1MacroQuest Core — MQ2Main.dll

The commands MacroQuest itself provides, available with no plugins loaded at all. MQ2Main.dll is MacroQuest — the module injected into eqgame.exe that supplies the command parser, the ${…} data and TLO system, the macro language, the chat-event and detour engine, and the plugin host that every DLL in plugins\ loads into. That makes this section the floor of the whole reference: nothing here depends on anything else being installed, whereas everything from §1.3 onward is a plugin layered on top and disappears if that plugin is not loaded. Several of these commands deliberately shadow an EverQuest command of the same name with an enhanced version — /target, /who, /camp and /assist among them — which is why /eqtarget exists to reach the client's original. The core's macro-only commands, which do nothing unless a .mac is running, are split out into §1.2.

MQ2Events, in practice. Triggers live in config\MQ2Events_<CharName>.ini (or a shared MQ2Events.ini), one [section] per event with exactly two keys, trigger and command. Matching is Lax/Blech 1.7.4: #*# is a wildcard, #1#–#9# capture into ${EventArg1..9}, everything else matches literally and case-insensitively, and the pattern must match the whole line — which is why triggers are wrapped in #*# at both ends. Four things that cost real debugging time on this install:
• The plugin hooks OnIncomingChat only, meaning chat received from the server. /echo and EQBC /bc output are written by MacroQuest rather than received, so neither can ever fire a trigger — testing a pattern with /echo proves nothing.
• /event off is global, not per-event. A command containing /event off … /docommand /timed 10 /event on disables every trigger for that window, and if the toon zones or dies before the timed restore comes due, the queued command is dropped and events stay off silently.
• /event load re-reads the INI and /event list will then show the new event — but appearing in that list is not proof it was registered with the matcher. If /eventdebug shows the line being fed and nothing matches, restart the client so the section is picked up during plugin init.
• /plugin MQ2Events unload crashed eqgame.exe on this build. To take it out of service, set MQ2Events=0 in config\MacroQuest.ini and restart instead.
Because the INI is read through the Win32 GetPrivateProfileString API, the file must be ANSI or UTF-8 without a BOM and use CRLF line endings; an editor that saves UTF-16 or bare LF produces a file that parses as empty, with no error. Where E3 is already running, [EventRegMatches] in the character INI does the same job with .NET regex and none of the above — see §3.8.

Command filter tokens narrow who acts on a broadcast

The first-argument target filter decides which toons receive a command. These four tokens are the second stage: each receiving toon evaluates them against itself and decides whether to run the command at all. Append them anywhere on the line — E3 strips them out while parsing, so they never reach the command's own arguments.

TokenWhat it doesExample
/only|listAllow-list — default deny. Only toons matching the list run the command; every other recipient silently ignores it./e3bcaa //quickburns /only|Tanks
/not|listDeny-list — default allow. Toons matching the list ignore the command; everyone else runs it. The inverse of /only|./e3bcaa //makemevisible /not|Ogrim
/include|listA second allow-list evaluated after /only| or /not| has been applied — use it to widen a filter without rewriting the first list./e3bc //looton /only|Tanks /include|Yhgrim
/exclude|listA second deny-list evaluated at the same stage — carves named toons or classes back out of whatever the first token let through./e3bc //followme /only|Melee /exclude|BRD
What goes in the list. Entries are separated by spaces, not commas, and every comparison is case-insensitive. Each entry may be a character name, a class short code, or one of the group keywords below, and you can mix all three in one list. E3's own help text for /e3restock shows the single-value shape: /e3restock emerald 500 /only|Healers.
A list of more than one entry must be quoted. E3 tokenises the command line on spaces before any of this runs — quote-aware, but spaces still split. So /only|Ogrim Yhgrim does not filter to two toons: the line breaks into /only|Ogrim and a stray Yhgrim, the filter sees one name, and the leftover word is handed to the command as an ordinary argument, which may well corrupt it. Wrap the whole list instead, so it survives as a single token and the filter's own space-split can do its job:
/e3bcaa //quickburns /only|"Ogrim Yhgrim"  ·  /e3bc //looton /not|"SHD WAR"  ·  /e3bc //followme /only|"Melee Tanks"
A single-entry list needs no quotes — /only|Healers is fine as written.

How the tokens combine, and the one that surprises people. /only| and /not| are mutually exclusive: if both appear, /only| wins outright and the /not| is never read. Repeating a token does not merge the lists either — the last occurrence of each token on the line is the one used, so /only|Tanks /only|Healers filters to healers alone. /include| and /exclude| are evaluated after whichever of the two ran, which is what lets you write /only|Melee /exclude|BRD. All four are matched on the token name alone, so the pipe is required: /only Ogrim with a space is not recognised as a filter and will be passed through to the command as an ordinary argument.
Source. Nothing in this subsection comes from E3's help text — the tokens are undocumented there. It was all read out of E3.dll's IL, disassembled with the bundled resources\Mono\32bit\bin\ikdasm.bat: EventProcessor::GetCommandFilters for which tokens are recognised, e3util::FilterMe for precedence and last-wins behaviour, e3util::FilterReturnCheck for the group keywords, and CommandMatch::set_args for the stripping and the ParseParms space-tokenising that forces the quoting rule. The keyword tables were cross-checked against the E3Core.Data.Class enum, whose Tank, Priest, Caster and Melee literals match the masks exactly. That means the semantics are as-implemented rather than as-intended, and none of it has been confirmed by running the commands in game.
Which commands honour them. The filter list is parsed off every E3 command as it is received, so appending a token is always safe. Acting on it is up to the individual handler, and not all of them check — the broadcast family (/e3bc and its suffixed variants), burn requests and /e3restock demonstrably do. If a token appears to be ignored, that handler simply does not consult the filter list; the token is still stripped, so nothing is corrupted. Verify against your own build with /e3listcommands.

E3 keeps its own named string variables — your custom flags. They are per-character and in memory only: not shared across the bot network, and not written to disk. Recipe · a manual "stop casting" flag. For an encounter where the mob is immune to everything you throw at it, gate every offensive line behind one switch.
1. In GlobalIfs.ini (§3.8): CanCast=!${Bool[${NoCasting}]}
2. On every nuke, debuff and DoT line: /Ifs|CanCast — or /Ifs|SafeToNuke,CanCast where a condition already exists.
3. In [Startup Commands] on each bot: Command=/e3varbool NoCasting False
4. In game: /e3bcaa //e3varbool NoCasting True to stop, False to resume.
Step 3 is not optional. Because substitution is plain text, an unset variable leaves the literal ${NoCasting} in the expression; MacroQuest cannot resolve it, ${Bool[]} reads that leftover text as true, and the toon stops casting. Check any toon with /e3varlist or /e3echobool ${CanCast}.

Ifs are text substitution, not evaluation. Before MacroQuest parses anything, E3 walks the expression three times: first replacing ${Name} for every E3 variable, then for every [Ifs] key (character INI, then GlobalIfs.ini), then over the variables once more so an Ifs that dragged in another Ifs still resolves. Only the finished string is handed to MacroQuest as ${If[…,TRUE,FALSE]}. Two consequences: an [Ifs] entry can freely reference another one by name, and any name that never matched is left in place as literal text for MacroQuest to choke on. Worked example from the tooltip. Announce a Life Support click to your group:
[Life Support] → Life Support=Divine Barrier/HealPct|20/Gem|7/AfterEvent|TellGroupIUsedDivineBarrier
[Events] → TellGroupIUsedDivineBarrier=/g I just used Divine Barrier!
/delay does not work in an event or a command set. /delay is a macro command — it pauses the execution block of a running .mac. E3 events, [CommandSets] and plugin-issued commands are not macros, so there is no block to pause and the command silently does nothing. MacroQuest prints an “isn't running” error for /call, /goto, /return, /endmacro and /pause, but has no such guard on /delay, which is why this failure is invisible rather than loud. /multiline compounds it by running every command in the same frame without ever yielding to the game loop. Use /timed <deciseconds> <command> instead — it is scheduled off MacroQuest's pulse and needs no macro. Its offsets are measured from the moment it is issued, so under /multiline they must be cumulative, not relative to the previous step:
GroupInvis=/multiline ; /target Ogrim ; /timed 5 /cast 8 ; /timed 60 /target Yhgrim ; /timed 65 /cast 8
That reads: target now, cast at 0.5s, retarget at 6.0s, cast again at 6.5s. /docommand is not a substitute — it forces an extra parse pass so TLOs expand before execution, and adds no timing of any kind.

Two caveats worth knowing. First, string extraction cannot always distinguish a command a plugin registers from one it merely issues — where a plugin's strings showed only generic commands like /stand or /autoinventory, those were treated as issued, not registered, and left out. Second, binary noise in large DLLs produces occasional false command-shaped tokens; entries that were plainly junk have been dropped. For E3 specifically there is no ambiguity — the registrations were read from IL, not guessed. Run /e3listcommands in game to confirm against your exact build.
